# Запуск двух профилей Codex: C1 и C2

## Работа и данные

Ярлык C2 вызывает launch_chatgpt2.vbs из постоянного каталога Multi-Account\code. Обёртка запускает помощник Folders/CSS, затем ChatGPT2Launcher.exe. Второй профиль хранится в %APPDATA%\Codex-Profile2. При замене launcher используются существующие авторизация, настройки и история.

Повторный клик передаёт событие работающему supervisor. Любая повторная активация, включая подключение нового supervisor к уже открытому C2, передаётся штатному обработчику единственного экземпляра Codex через тот же алиас и окружение профиля. Supervisor не показывает и не фокусирует HWND самостоятельно: видимость окна Windows не гарантирует видимость содержимого Electron. Иконка — ChatGPT2.ico, группа панели задач — OpenAI.Codex.Profile2. Пересоздание окна (уничтожение старого HWND с созданием нового) не завершает приложение, однако с 19 октября 2026 года закрытие живого окна крестиком (`X`, скрытие в системный трей: `IsWindow(hwnd) && !IsWindowVisible(hwnd) && !IsIconic(hwnd)`) приводит к полному выходу C2 (штатный `quit-app` через UI-помощник и остановка дерева процессов `C2Process.StopOwnedTree` со стороны supervisor). Сворачивание в панель задач (`_`, `IsIconic`) сохраняет работу приложения. Обновление значка и заголовка использует SWP_NOACTIVATE.

## Обновления приложения

Постоянная защита от двух сбоев добавлена 17 октября: C1 теперь запускается через `c1-runtime.ps1 -Launch` с синхронной регистрацией staged-пакета (когда процессы пакета закрыты) и активацией через `IApplicationActivationManager` с портом 9223 (прямой `CreateProcessW` по физическому пути в `WindowsApps` блокируется Windows ACL `WIN://SYSAPPID` с кодом 5). Работающий помощник также наблюдает штатный запрос обновления и после выхода старого C1 завершает регистрацию и открывает новую версию с нужным параметром. Если Windows уже открыла новый процесс без порта, допускается одно штатное исправление только в первые 20 секунд его жизни и при отсутствии активных ответов. Обычный выход и давно работающие сессии не вызывают автоперезапуск. Успех подтверждается новой версией и подключёнными Folders/CSS. Условия и ограничения: [руководство UI](../../UI/KB/README.md).

Обновление общей установки выполняется из C1. Для дочернего C2 задаётся CODEX_SPARKLE_ENABLED=false: этот параметр установленного Codex отключает второй установщик обновлений. Он не меняет окружение C1. Это устраняет повторное скачивание общего MSIX-пакета и дублирующую синюю кнопку в C2. При следующем запуске C2 выбирает зарегистрированную Windows версию по алгоритму ниже.

Если кнопка обновления закрывает Codex без перезапуска, а после ручного запуска появляется снова, сначала сравните зарегистрированный пакет текущего пользователя с подготовленными пакетами Windows. Наличие новой папки в WindowsApps само по себе не означает завершения установки. Источник ошибок — журнал Microsoft-Windows-AppXDeploymentServer/Operational; журналы самого приложения находятся в %LOCALAPPDATA%\Codex\Logs.

17 октября обновление с 26.1013.3656.0 до 26.1013.4894.0 дважды остановилось на регистрации: события 419/401/404 содержали 0x800700E9 «нужно закрыть OpenAI.Codex_2p2nqsd0c76g0!App», итоговый HRESULT — 0x80073CF9. Новая версия оставалась Staged, старая — Installed. Обе версии были исправно подготовлены; очистка кеша, повторное скачивание и переустановка профилей не требовались. Точный процесс, мешавший регистрации в момент этих попыток, по сохранённым событиям не установлен. На момент диагностики C2 был закрыт, а среди процессов с идентичностью пакета работало только дерево C1; внешний помощник UI этой идентичности не имел.

Для подготовленного пакета запрошена регистрация через публичный PackageManager.RegisterPackagesByFullNameAsync с RegisterPackageOptions.DeferRegistrationWhenPackagesAreInUse=true. ForceAppShutdown, ForceTargetAppShutdown и DeveloperMode оставлены false. Windows вернула HRESULT 0, IsRegistered=false и успешную OnDemandRegisterOperation: это подтверждение отложенной регистрации, а не уже работающей новой версии. Такой режим завершает регистрацию при следующей активации приложения. Нужно полностью выйти из C1/C2, включая работу в трее, и открыть C1 штатным ярлыком. Результат подтверждается новой зарегистрированной версией, путём нового процесса и подключением Folders/CSS. До этого обновление нельзя считать полностью завершённым.

Для работы с модулем Appx используется Windows PowerShell 5.1 по абсолютному пути %WINDIR%\System32\WindowsPowerShell\v1.0\powershell.exe: импорт Appx в PowerShell 7 на этой машине не поддерживается. Для восстановления выбирается только более новый подготовленный пакет той же семьи через API Windows; версия и путь из приведённого случая не должны зашиваться в launcher. Отложенная регистрация не требует дополнительных фоновых задач, новых ярлыков, временных скриптов или изменения файлов установленного Codex.

Документация Microsoft: [разница между staging и регистрацией](https://devblogs.microsoft.com/insidemsix/add-vs-stage-and-register/), [RegisterPackagesByFullNameAsync](https://learn.microsoft.com/en-us/uwp/api/windows.management.deployment.packagemanager.registerpackagesbyfullnameasync), [DeferRegistrationWhenPackagesAreInUse](https://learn.microsoft.com/en-us/uwp/api/windows.management.deployment.registerpackageoptions.deferregistrationwhenpackagesareinuse).

1. `CodexPackage.cs` получает зарегистрированные пакеты текущего пользователя через `GetPackagesByPackageFamily`/`GetPackagePathByFullName` и подготовленные (staged) обновления через `GetStagedPackagePathByFullName` (`kernelbase.dll`) совместно с `StateRepository`/`AppxAllUserStore`/`WindowsApps` без требования повышенных прав; метод `CodexPackage.Available()` объединяет оба набора по убыванию версии.  
2. `CodexPackage.EnsureRegistered` и `EnsureLatestRegistered` всегда регистрируют старшую валидную версию из `Available()`, перед регистрацией при отсутствии открытых окон `ChatGPT.exe` завершают осиротевшие фоновые процессы контейнера (`codex.exe`, `conhost.exe`) и выполняют до трёх попыток регистрации на случай задержки освобождения контейнера со стороны `AppXDeploymentServer`.  
3. EXE и ID основного приложения читаются из `AppxManifest.xml`, где имя `ChatGPT.exe`, подпапка `app`, версия и ID `App` не зашиты в алгоритм.  
4. Выбирается старшая доступная версия с валидным манифестом и EXE, а неполная или удалённая (`ERROR_NOT_FOUND = 1168`) установка исключается до запуска.  
5. `AppExecLink.cs` читает содержимое NTFS-алиаса, ремонтирует отсутствующий или устаревший алиас и проверяет результат чтением, не переписывая актуальный алиас.  
6. `C2Process.cs` запускает алиас напрямую через `CreateProcessW`, передаёт отдельное окружение дочернему процессу и получает его реальный PID без промежуточного `cmd.exe`.  
7. Для подключения к открытому C2 и проверки процессов пакета в `CodexPackage.cs`, `C2Process.cs` и `C1Runtime.cs` используются прямые вызовы Win32/NT API (`QueryFullProcessImageName`, чтение командной строки из PEB и `NtQueryInformationProcess` за ~13 мс) вместо WMI `Win32_Process`, что полностью устраняет ошибки `Quota violation` (`0x8004106C`) и зависания опроса.  
8. Иконки, код и профиль находятся вне каталога версии MSIX, а пути `%APPDATA%` и `%LOCALAPPDATA%` берутся из одноимённых переменных окружения с резервом `Environment.GetFolderPath`.

Решение поддерживает обычную замену версии, пути, имени EXE и ID приложения при сохранении одного видимого приложения в манифесте. Оно зависит от сохранения семейства пакета OpenAI.Codex_2p2nqsd0c76g0 и переменных CODEX_HOME и CODEX_ELECTRON_USER_DATA_PATH. Изменение этих механизмов OpenAI потребует адаптации. Неоднозначный манифест и неподдерживаемые изменения дают явную ошибку.

## Рабочие компоненты

- ChatGPT2Launcher.cs — мьютекс, событие активации, окно и supervisor.
- CodexPackage.cs — регистрация пакета и манифест.
- AppExecLink.cs — чтение, ремонт и проверка алиаса.
- C2Process.cs — запуск и проверка принадлежности процессов.
- launch_chatgpt2.ps1 и launch_chatgpt2.vbs — обёртки одного launcher.
- build.ps1 — воспроизводимая сборка .NET Framework.
- tests\LauncherTests.cs — проверки обновлений, алиасов и изолированного запуска.
- tests\AliasActivationRegression.cs — настоящий холодный запуск Codex и первая активация из скрытого GUI-процесса.
- tests\SupervisorRegression.cs и tests\WindowLifecycleHost.cs — проверки supervisor при скрытии, восстановлении и пересоздании окна.
- tests\TestWorkspace.cs — отдельные каталоги и уникальные имена тестовых профилей.

Старые прототипы управления значком, пробные сборки, снимки панели задач и временные профили убраны из рабочих каталогов. Рабочие исходники, иконки и воспроизводимые тесты сохранены.

## Folders и компактный UI

C1/C2 автоматически подключают модули папок и оформления через отдельный помощник Node.js. Эти модули не изменяют установленный пакет Codex. Подробности, управление и восстановление исходного ярлыка: [руководство UI](../../UI/KB/README.md).

Помощник подключается к C1 после обновления через порт 9223. Если Windows запустила C1 без этого параметра, по умолчанию показывается waiting-for-manual-launch: автоматический перезапуск отключён. После завершения работы можно полностью выйти из C1 и открыть его штатным ярлыком. Исходники также содержат отдельный явно включаемый механизм штатного восстановления; он не применяется автоматически в текущей конфигурации.

## Сборка и проверка

Перед заменой EXE завершите supervisor либо собирайте в отдельный каталог. Из каталога code:

~~~powershell
.\build.ps1 -OutputDirectory 'C:\path\to\staging' -Test
~~~

Реальный запуск в новом временном профиле:

~~~powershell
.\build.ps1 -OutputDirectory 'C:\path\to\staging' -RuntimeTest
~~~

Проверки включают смену имени EXE и ID приложения, сравнение версий, неполную установку, исчезнувший старый путь, создание и удаление алиаса, защиту чужого файла и алиаса, принадлежность процесса и передачу окружения только дочернему экземпляру. Runtime-проверка открывает временное окно Codex и завершает только созданное тестом дерево.

Все тестовые EXE, журналы и профили создаются в отдельном каталоге TEMP и удаляются в finally. Тесты используют уникальные имена c2-launcher-test-<id>-runtime/startup; соответствующие профили браузера также удаляются. В OutputDirectory остаётся только запрошенный рабочий ChatGPT2Launcher.exe. Каталоги с одноразовой диагностикой исключены из Git.

## Диагностика

Проверка жизненного цикла окна с отдельным тестовым приложением:

~~~powershell
.\build.ps1 -OutputDirectory 'C:\path\to\staging' -Test -LifecycleTest
~~~

Регрессия воспроизводилась со старым supervisor: скрытие окна дольше двух секунд приводило к принудительному завершению процесса. Проверки требуют сохранения процесса при скрытии и при шестисекундном пересоздании окна, восстановления по повторной активации и выхода supervisor после фактического завершения приложения. Отдельно воспроизводится состояние, когда рамка Windows видна, а содержимое приложения остаётся скрытым: повторная активация обязана обратиться к приложению даже при видимом HWND. Тестовое окно находится за пределами рабочего стола, не отображается в панели задач и не активируется. Проверка 17 октября: 16 основных проверок и 6 проверок жизненного цикла прошли.

%APPDATA%\Codex-Profile2\launcher.log содержит выбранный EXE, ID приложения, PID, результат активации и причины ошибок. Рабочий журнал хранится с данными профиля, а не среди исходников.

После холодного запуска supervisor только назначает значок и группу; показ окна выполняет сам Codex. Прежние вызовы ShowWindow/ShowWindowAsync, BringWindowToTop и AttachThreadInput из пути активации удалены. Синхронный ShowWindow из скрытого VBS-лаунчера ранее скрывал уже открывшееся окно; замена его на ShowWindowAsync устранила тот симптом, но не обеспечила согласованное восстановление содержимого Electron.

Опциональная RuntimeTest по-прежнему запускает настоящий Codex из скрытого GUI-процесса и проверяет видимость первого окна в течение 1,5 секунды. Она открывает окно приложения, поэтому при работе пользователя на компьютере её запускать не следует. 17 октября этот тест не запускался; проверялись основные алгоритмы и отдельное фоновое тестовое приложение.

При зависшем изображении нужно отдельно проверять состояние процесса, видимость HWND и document.visibilityState. 17 октября процесс C2 и JavaScript отвечали, но document.visibilityState оставался hidden при видимом, неминимизированном окне. В 05:41:53 старый launcher восстановил HWND напрямую. Системный dwm.exe был перед этим запущен заново в 05:41:01; пользователь сообщил о запуске ярлыка «Перезапуск DWM». Этот скрипт принудительно завершает dwm.exe. Связь сбоя отрисовки с перезапуском DWM возможна, но одной временной последовательности недостаточно для доказательства. Баннер исчерпания кредитов объясняет ограничение новых запросов, но не неработающий ввод во всём окне.

Восстановить алиас без открытия приложения:

~~~powershell
.\ChatGPT2Launcher.exe --repair-alias
~~~

Код завершения: 0 при успехе, 1 при ошибке. Все точки входа C2 используют одну реализацию; PowerShell не компилирует отдельные помощники и не меняет окружение родительского сеанса.

API Windows: [GetPackagesByPackageFamily](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getpackagesbypackagefamily), [GetPackagePathByFullName](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getpackagepathbyfullname), [GetPackageFamilyName](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getpackagefamilyname).
