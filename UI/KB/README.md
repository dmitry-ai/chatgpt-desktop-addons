# Подключение Folders, CSS и общих проектов к Codex

## Работа

Открывайте C1 и C2 прежними ярлыками. Они запускают один общий скрытый помощник Node.js для Folders, CSS и [общих проектов](../../Shared-Projects/KB/README.md#обычная-работа). Его повторный запуск завершается при наличии уже работающего экземпляра. Новые окна открывайте через штатное верхнее меню Codex: помощник обнаружит их и применит оформление и общий каталог автоматически, обычно в течение двух секунд.

Приложение можно оставлять открытым при редактировании CSS и клиентского `Folders/code/renderer.js`. Эти файлы перечитываются автоматически. Изменение JavaScript самого помощника требует его остановки и повторного запуска.

После обновления Windows может перезапустить C1 без `--remote-debugging-port=9223`: штатный обновлятор регистрирует пустые аргументы перезапуска. Файлы Folders/CSS и общий каталог при этом сохраняются, но помощник теряет доступ к окну. Автоматический перезапуск по умолчанию отключён; состояние такого C1 — `waiting-for-manual-launch`. После завершения работы полностью выйдите из C1 и откройте его штатным ярлыком: он передаёт нужный параметр. Отдельный явно включаемый механизм восстановления в исходниках сначала дожидается завершения активных ответов и пяти секунд без записи в журналы сессий.

С 17 октября C1.lnk через существующую VBS-обёртку вызывает `c1-runtime.ps1 -Launch`. Если C1 ещё не открыт, он сначала проверяет наличие подготовленного обновления и при отсутствии запущенных процессов пакета синхронно завершает регистрацию (`DeferRegistrationWhenPackagesAreInUse=false`), после чего активирует зарегистрированный пакет через `IApplicationActivationManager` с портом 9223 и проверяет наличие порта у созданного процесса (прямой вызов `CreateProcessW` для EXE внутри `WindowsApps` без токена `WIN://SYSAPPID` отклоняется Windows с `ERROR_ACCESS_DENIED`). AUMID и версия берутся из публичных API Windows и манифеста. Профиль, окружение и штатный обновлятор C1 сохраняются. Если другой профиль удерживает подготовленное обновление, отложенная регистрация не ставится в очередь и старый пакет не выдаётся за успешно обновлённый: пользователю сообщается о необходимости полного выхода из C1/C2. Уже открытый C1 без порта не закрывается по обычному клику ярлыка.

`UpdateRecovery` в помощнике обрабатывает только наблюдавшийся запрос обновления: точную запись `update_resume_state_saved` в журнале известного PID C1 после времени рождения этого процесса.  
Обычный выход не вызывает автозапуск.  
После выхода всех окон старого пакета помощник очищает осиротевшие фоновые процессы контейнера (`codex.exe`, `conhost.exe`), синхронно регистрирует старшую доступную версию (`CodexPackage.Available()` — объединение зарегистрированных и staged-пакетов через `GetPackagesByPackageFamily` и `GetStagedPackagePathByFullName` без требования повышенных прав) и открывает новую зарегистрированную версию через `IApplicationActivationManager` с портом 9223.  
Если в момент завершения `Add-AppxPackage -Register` служба Windows (`[LaunchProcess]`) параллельно успевает запустить экземпляр без порта 9223, `C1Runtime.Launch` штатно закрывает этот новорождённый процесс и повторно активирует приложение с портом 9223.

Если штатный обновлятор Store завершился с `0x800700E9` (`PackagesInUseClosed` из-за задержки выгрузки фонового дерева `codex.exe`) и Windows сама перезапустила прежнюю или новую версию без порта, `UpdateRecovery` в первые 20 секунд жизни этого новорождённого процесса (при отсутствии активных ответов и после периода покоя) штатно закрывает его, завершает регистрацию staged-обновления и запускает новую версию с портом 9223.  
Работающий дольше C1 остаётся под управлением пользователя.  
Попытка ограничена двумя минутами и не зацикливается.  
Успех требует более новой версии пакета, параметра запуска и фактического подключения Folders/CSS и общего каталога.  
`status.update` показывает стадии `watching`, `waiting-for-updater-exit`, `registering`, `waiting-for-other-apps`, `waiting-for-turns`, `waiting-for-ui`, `verified` или `error`.  
Новый запрос `update_resume_state_saved` от нового процесса C1 разблокирует `UpdateRecovery` даже после прежней ошибки.  
Опрос процессов в `C1Runtime.cs` и `CodexPackage.cs` выполняется через прямые Win32/NT API (`QueryFullProcessImageName`, чтение командной строки из PEB, `NtQueryInformationProcess`) за ~13 мс без использования WMI (`Win32_Process`), что исключает ошибки `Quota violation` и таймауты worker-процесса.  
Разрешение домашнего каталога в `paths.mjs` и `ensure-ui.vbs` опирается на `LOCALAPPDATA`/`APPDATA`, поэтому вызов `manage.mjs` из сред с переопределённым `USERPROFILE` подключается к тому же именованному каналу и профилю C1.

Наблюдение зависит от штатной записи журнала Codex и формата идентичности пакета. Изменение этого контракта может потребовать адаптации; совместимость с любым будущим обновлением не гарантируется. Запуск из ярлыка работает независимо от этой записи. Уже запущенный без порта C1 нужно один раз полностью закрыть и открыть ярлыком. При загрузке страницы ещё не готовый сервис проектов повторно проверяется примерно через секунду, а не объявляется неподдерживаемым на 30 секунд.

Если обновление закрывает приложение, но синяя кнопка остаётся после ручного запуска, проверьте завершение регистрации MSIX. 17 октября Windows оставила новую версию в состоянии Staged из-за ошибки «нужно закрыть Codex». Порядок диагностики и подтверждения результата описан в [руководстве C1/C2](../../Multi-Account/KB/.md#обновления-приложения). Закрытый C2 и отсутствие подключённого клиента C2 в `status` сами по себе не означают неисправность синхронизатора.

Каталог установки Codex и `app.asar` не меняются. Логика `ChatGPT2Launcher.exe`, изоляция авторизации C2, его иконка и группа панели задач сохранены. У C2 ярлык теперь вызывает прежний `launch_chatgpt2.vbs`, который запускает помощник и затем тот же EXE supervisor. Резервная копия исходного ярлыка сохранена локально.

## Устройство

`UI/code/daemon.mjs` подключается только к страницам оболочки `app://-/index.html` на существующих отладочных портах C1:9223 и C2:9224. Страницы браузера, плагины, avatar overlay и предварительно загруженные окна Pages пропускаются. Перед подключением проверяется наличие bridge оболочки Codex.

Управление помощником использует локальный именованный канал Windows; новый сетевой сервер не открывается. Folders передаёт по binding операции с папками и решения конфликтов. Одна очередь записи и один каталог объединяют проекты и дерево C1/C2; для каждого профиля готовится проекция с его штатными ID и состоянием раскрытия. См. [Shared-Projects](../../Shared-Projects/KB/README.md#хранение-и-устройство).

`recovery.mjs` проверяет метаданные начала/завершения ответов в `CODEX_HOME/sessions` и запись подготовки обновления в `%LOCALAPPDATA%/Codex/Logs`; текст чатов не сохраняется и не передаётся. `c1-runtime.ps1` содержит один скрытый worker с приватным stdio. Он загружает `C1Runtime.cs` и общий с C2 `CodexPackage.cs` в память; дополнительных EXE, задач планировщика или копий приложения нет. Вне наблюдавшегося запроса обновления отсутствующий или уже работающий с портом C1 не перезапускается.

Перед восстановлением проверяются семья пакета, каноническая командная строка C1, PID и точное время рождения процесса. Алиас C2 исключается из выбора. [Restart Manager](https://learn.microsoft.com/en-us/windows/win32/api/restartmanager/nf-restartmanager-rmshutdown) получает ровно один закреплённый процесс и флаг `RmShutdownOnlyRegistered`, без принудительного завершения. Новый и повторный запуск C1 выполняется через `IApplicationActivationManager::ActivateApplication` с портом 9223 и проверкой идентичности пакета и порта. Номер версии и путь WindowsApps в коде не закреплены. При отказе приложения, непонятном формате журналов или ошибке чтения автоматические попытки прекращаются; ошибка видна в `status` и `ui.log`.

Проектные узлы не перемещаются между DOM-родителями. Добавляются собственные строки папок и кнопки назначения; штатным элементам задаются CSS order, отступ и видимость. Смешанные списки Pinned не перестраиваются.

Подключение зависит от внутренних атрибутов сайдбара, отладочного интерфейса и сервиса проектов Desktop App. После совместимого обновления оно восстанавливается автоматически; изменение внутренних контрактов может потребовать адаптации. При неподходящей структуре список проектов не перестраивается. Пароли и токены помощник не читает. При первичной миграции сохраняются резервные копии глобального состояния и базы профиля; синхронизатор работает с метаданными проектов. См. [обновления](../../Shared-Projects/KB/README.md#обновления-приложения).

## Установка и запуск

Нужен уже установленный Node.js 22.16 или новее. Установка на текущей машине:

```powershell
& 'C:/work/research/provision/code/AI/products/OpenAI/ChatGPT/Desktop/Addons/code/UI/code/install.ps1'
```

Скрипт сохраняет исходные обёртки и C2.lnk в `UI/code/state/installation`, добавляет запуск помощника и запоминает путь Node.js в `node-path.txt`. Повторная установка не добавляет дублирующих строк.

Запустить помощник без открытия или активации Codex:

```powershell
Start-Process wscript.exe -ArgumentList '"C:/work/research/provision/code/AI/products/OpenAI/ChatGPT/Desktop/Addons/code/UI/code/ensure-ui.vbs"' -WindowStyle Hidden
```

По умолчанию C1 использует `%USERPROFILE%/.codex`, C2 — `%APPDATA%/Codex-Profile2`. Для нестандартных путей задайте `CODEX_UI_C1_HOME` и `CODEX_UI_C2_HOME` в окружении помощника перед его запуском.

## Диагностика

```powershell
node 'C:/work/research/provision/code/AI/products/OpenAI/ChatGPT/Desktop/Addons/code/UI/code/manage.mjs' status
node 'C:/work/research/provision/code/AI/products/OpenAI/ChatGPT/Desktop/Addons/code/UI/code/manage.mjs' state C1
node 'C:/work/research/provision/code/AI/products/OpenAI/ChatGPT/Desktop/Addons/code/UI/code/manage.mjs' reload
```

`status` показывает PID, общий каталог, число проектов и папок, конфликты, ожидающие изменения и подключённые окна. Поле `recovery` отражает восстановление C1: `waiting-for-manual-launch` — C1 запущен без порта, автоматический перезапуск отключён; `waiting-for-turns` — есть активные ответы, `waiting-for-idle` — выдерживается пауза, `waiting-for-verification` — C1 перезапущен, `connected` — окно подключено, `error` — восстановление остановлено. Состояния ожидания ответов и автоматического перезапуска относятся к явно включённому восстановлению. Отсутствие окна закрытого профиля нормально. События подключения и ошибки находятся в `UI/code/ui.log`; успешное повторное внедрение отмечается строкой `C1 UI recovery verified: Folders/CSS installed`.

Для применения изменения кода самого помощника выполните `manage.mjs stop`, затем запустите `ensure-ui.vbs`. Окна Codex перезапускать не требуется.

С 19 октября 2026 года модуль Folders отключает прерывание чата обычным Esc в C1/C2. Esc закрывает меню и диалоги; терминалы и редакторы кода сохраняют собственную обработку этой клавиши. Это правило UI-помощника, а не переназначение команды в штатной настройке Keyboard Shortcuts. При установке `daemon.mjs` через CDP ставит защитный обработчик перед обработчиком композера, сохраняя относительный порядок и параметры остальных слушателей. Учитывается обёртка Sentry. Для зависшего штатного Electron-меню используется штатный `electronBridge.showContextMenu([])`, возвращающий `{id: null}`; окна и процессы приложения не закрываются.

С 19 октября 2026 года закрытие главного окна крестиком (`X`) в C1 и C2 выполняет реальный выход вместо скрытия в системный трей. В штатном `app.asar` обработчик `close` скрывает окно (`z.hide()`), а значок трея у C1 и C2 использует один и тот же жёстко зашитый GUID `e5768d8b-6936-4f45-b1ad-4c5fb414cb35`, из-за чего одновременный запуск C1 и C2 приводил к потере значка трея у первого экземпляра и оставлял скрытое дерево процессов (`ChatGPT.exe`, `codex.exe`, `node_repl.exe`, `codex-computer-use-swift.exe` и др.) работать в фоне без иконки. Теперь при переходе `document.visibilityState` в `hidden` помощник проверяет окно через `C1Runtime.ProbePortWindow`: при сворачивании (`_`) окно остаётся `IsWindowVisible && IsIconic` и продолжает работать, а при закрытии крестиком (`!IsWindowVisible && !IsIconic`) помощник отправляет штатный `window.electronBridge.sendMessageFromView({type: 'quit-app'})` с контрольным завершением через `C1Runtime.CloseHiddenProcess`. Тот же контроль работает в `C1Recovery` для C1 без порта 9223 и в `ChatGPT2Launcher.exe` для C2.

Проверки восстановления:

```powershell
node 'C:/work/research/provision/code/AI/products/OpenAI/ChatGPT/Desktop/Addons/code/UI/code/recovery.test.mjs'
& 'C:/work/research/provision/code/AI/products/OpenAI/ChatGPT/Desktop/Addons/code/UI/code/test-native.ps1'
```

Проверяются незавершённые и прерванные ответы, частичные записи, остановка помощника, отказ Windows, обычный выход без автозапуска, ожидание другого профиля, незавершённая регистрация, потеря параметра после обновления, готовность UI и отсутствие циклов. Нативная проверка проверяет разрешение AUMID и пути EXE зарегистрированного пакета через API Windows, а также штатное закрытие только собственного тестового процесса через Restart Manager; соседний процесс и C1 остаются живы. Формы теста находятся вне экранов и не активируются. Активация настоящего C1 требует явного `-AllowAppActivation` и по умолчанию не выполняется. Временная сборка создаётся в уникальной подпапке TEMP и в `finally` отправляется в Корзину.

## Отключение

```powershell
& 'C:/work/research/provision/code/AI/products/OpenAI/ChatGPT/Desktop/Addons/code/UI/code/uninstall.ps1'
```

Помощник удалит внедрённые элементы и стили из открытых окон; скрипт восстановит исходные обёртки и C2.lnk. Общий каталог, резервные копии и прежние конфигурации папок в профилях останутся. Если обёртка или ярлык были дополнительно изменены после установки, автоматическое восстановление остановится, сохранив эти изменения.

Для временного отключения до следующего запуска ярлыка достаточно `manage.mjs stop`. Штатные проекты и чаты не удаляются ни при одном варианте отключения.
